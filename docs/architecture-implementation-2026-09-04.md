# Первый пакет архитектурных изменений MIGTORG

Статус: экспериментальная поставка в рабочем дереве, без выпуска и без переключения основной маршрутизации. Область пакета — измерения, сквозные ограничения и первый эксперимент выбора сценария. Этапы 3–6 исходного плана не считаются выполненными.

## Изменения

1. Manifest v2 включает код приложения и evaluator, всю БЗ, policy/config, scorer, feature schema, обе конфигурации порогов, виджет, зависимости, флаги архитектуры и фактически загруженный dense-канал. Для загруженного encoder фиксируются checksum весов и доступная revision. До инициализации доступность обозначена как неизвестная.
2. Роли сценариев сохраняются в поисковых карточках. Одинаковая проверка действует в Top-10, альтернативном поиске, получении карточки по ID, финальном выборе, генераторе и списке действий. Закрытые карточки не становятся гостевыми при преобразовании.
3. Действие принимается только из последнего ответа этой сессии, с повторной проверкой текущей роли. При наличии `conversation_turn_id` он должен совпадать с предыдущим ответом. Для старого клиента без этого поля используется последний сохранённый ответ.
4. SQLite расширена таблицами `response_states`, `decision_traces`, `llm_budget_reservations`. История и обращения не удаляются. Чтение уточнения обращается к SQLite, поэтому новый worker видит состояние другого worker. Это основа состояния, а не полная реализация понимания свободных продолжений из этапа 3.
5. Ошибка кодирования запроса или scorer приводит к уточнению. Лексический шаблон не может превратить отказ без карточки в уверенный ответ.
6. Произвольный fallback больше не признаётся утверждённым шаблоном. Детерминированный быстрый путь разрешён только для опубликованного answer contract. Неподтверждённые Python-исключения заменяются контрактом; факты БЗ не менялись.
7. Три опубликованных knowledge gap исполняются при выборе соответствующего сценария и совпадении предмета вопроса. Ответ берётся из `safe_answer`, возвращается состояние уточнения. Распознавание вариаций gap пока ограничено явными правилами, а ошибочная маршрутизация к другой теме остаётся ограничением.
8. У status action тарифа reference — подтверждённый пользователь, у операций по лоту — lot ID. Справочный ответ не приобретает это требование. Полная валидация контрактов бизнес-систем относится к этапу 5.
9. Появились необязательные поля ответа `state_version`, `action_result`. Предложение обращения, создание и подтверждение доставки различаются. Новый слой не объявляет письмо доставленным на основании записи в БД; доставка помечается `unconfirmed` до отдельной интеграционной реализации.

## Варианты и переключатели

| Настройка | Значение по умолчанию | Назначение |
|---|---|---|
| `ROUTING_ARCHITECTURE` | `control` | A: прежний маршрут с новыми ограничениями; `local`: единый scorer B |
| `LLM_UNDERSTANDING_ENABLED` | `false` | C: ограниченный выбор среди тех же кандидатов поверх локального решения |
| `ARCHITECTURE_EXPERIMENT` | `true` | Отключает пользовательскую LLM-переформулировку независимо от настройки выбора |

В B scorer принимает окончательное решение; второго независимого high-confidence fallback нет. Лексические и предметные совпадения используются имеющимися признаками scorer. Новой обученной модели понимания цели или полного переноса всех признаков старых профилей в новый feature schema в этом пакете нет: способность существующего scorer заменить ранние правила проверяется отдельно.

C использует текущую провайдерную границу и основную модель, обезличенную реплику, ID предыдущего сценария и поисковые описания Top-10. JSON допускает только цель и допустимый ID либо недостающий признак. Неизвестный ID, лишние поля, ошибка провайдера и исчерпание бюджета возвращают локальное решение. Запрос не содержит бизнес-инструментов. Перед вызовом резервируется бюджет в SQLite; настройки внешнего timeout ограничены четырьмя секундами и остатком пятисекундного времени ответа. Реальный p95 этой ветки не подтверждён без настроенного провайдера и нагрузочной проверки.

## Калибровка и данные

`configs/reranker_config.json` сохранён для контрольной ветки. Старый отчёт калибровки не объявляется доказательством его актуального качества.

`configs/architecture_reranker_config.json` получен для **сохранённого runtime artifact**, а не переобученной копии, на 400 development-случаях. Семейство выбирается по предсказанному сценарию, как в runtime. Файл содержит SHA artifact и входов; при несовпадении artifact кандидат закрывает ответ. Пороги нельзя интерпретировать как откалиброванную вероятность правильного ответа на естественном трафике: использован существующий snapshot кандидатов, независимой проверки этих порогов ещё нет.

Калибровка не читает контрольные 270 запросов. БЗ, шаблоны, scorer artifact и исходные метки не переписывались. Для контрольного прогона применяется существующий approved overlay с проверкой SHA исходного корпуса. Конфликты между старой меткой и ролью гостя перечисляются отдельно, без изменения меток.

## Воспроизведение

Из корня репозитория, в окружении с зависимостями проекта:

```powershell
$env:OMP_NUM_THREADS = '1'
$env:MKL_NUM_THREADS = '1'
python -B -m backend.tools.calibrate_runtime_scorer --output .work/calibrated-reranker-config.json
python -B -m backend.tools.evaluate_architecture
```

Evaluator использует временную SQLite, запрещает доставку писем, status API, загрузку модели из сети и пользовательскую переформулировку. Сам scorer и encoder выполняются. A/B проходят весь обработчик напрямую и через ASGI HTTP endpoint; их кандидаты сравниваются. D подставляет допустимый эталонный сценарий только внутри evaluator, сохраняя safety и остальные слои приложения. Runtime не имеет oracle-переключателя.

Для C предусмотрен `--include-llm`; нужны существующие backend-настройки провайдера, цен и бюджетов. Без них C не считается исполненным. Локальный mock не засчитывается за LLM-эксперимент.

Артефакты:

- `reports/architecture-original-baseline.json`: свежий pre-change replay исходной реализации `bd3a92a`, 220/270 маршрутов, 215/270 автоматических answer checks, 40 уверенно неверных маршрутов. Это историческая точка, не результат нового runtime.
- `reports/architecture-experiment.json`: агрегаты нового прогона, manifest каждой ветки, HTTP-паритет, неизменность bundle, конфликты ролей, раздельные метрики обращений.
- `.work/architecture-experiment-details.json`: локальные покейсные ответы и диагностические трассы.
- `.work/architecture-full-suite.xml`: результат полного запуска pytest.
- `reports/architecture-regression-comparison.json`: покейсное сравнение падений с изолированной копией `bd3a92a`.

Отчёты с проверкой фрагментов ответа помечены как **automatic proxy**, а независимая экспертная оценка — `null`. В тестах этапов 3–4 исторические отчёты помечены `report_snapshot`; их зелёный результат не подтверждает готовность нового runtime. Для свежих поведенческих проверок можно исключить их через `-m 'not report_snapshot'`.

## Полная регрессия

Окончательный A/B/D-прогон завершён на неизменном bundle; Top-10 A и B полностью совпал, расхождений между прямым вызовом и HTTP не было.

| Ветка | Автоматические проверки полного ответа | Уверенно неверные ответы / high | p95 обработчика после прогрева |
|---|---:|---:|---:|
| A — контроль с ограничениями | 212/270 (78,52%) | 40/236 (16,95%) | 526 мс |
| B — единый scorer с отдельной калибровкой | 85/270 (31,48%) | 21/97 (21,65%) | 232 мс |
| D — допустимый эталонный сценарий | 227/239 (94,98%) | диагностический показатель | 74 мс |

Для корректного сравнения с D на тех же 239 случаях: A — 203/239, B — 81/239, D — 227/239. Это подтверждает полезность устранения ошибок выбора, но **не** подтверждает пригодность текущего scorer для этой задачи. У B 176 уточнений из 270: снижение абсолютного числа уверенных ошибок достигнуто вместе с резким падением доли отвеченных запросов.

Recall@10 на случаях с допустимой меткой — 233/239 (97,49%). В полном корпусе 19 конфликтов ожидаемого сценария с гостевой ролью, ещё 12 случаев без конкретного положительного scenario ID; они не включены в диагностический D и не исправлялись автоматически. На 251 случае без конфликта ролей A даёт 84,46% автоматических answer checks, B — 33,86%; этот срез не заменяет полный корпус и независимый gate.

В D обнаружены пять попаданий запрещённых маркеров офисного адреса из текущего утверждённого шаблона. Их нужно отдельно сопоставить с актуальными первичными источниками и ожиданиями evaluation; это не свидетельство пяти экспертно подтверждённых нарушений и не основание автоматически переписать БЗ.

Локальные времена ниже пяти секунд. Для B p95 также ниже исходных 357 мс. У A диагностическая обвязка увеличила p95 примерно на 47%; поэтому ограничение относительной деградации 10% для контрольной локальной ветки не подтверждено. Продакшен-нагрузка, сетевое время виджета и C этим замером не проверены. Причины неготовности нельзя свести только к задержке.

**Решение: B не продвигается; C не оценён на внешнем провайдере; выпуск закрыт.**

Полный запуск: **633 passed, 43 failed**. Все 43 упавших случая повторены в отдельной копии исходного `bd3a92a` с теми же локальными datasets: **30 failed, 13 passed**. Это проверка происхождения конкретных падений, а не утверждение, что весь исходный suite был зелёным.

Финальный профильный прогон на окончательном коде: **40 passed**. Проверены границы доступа, происхождение fallback, ошибки модели, персистентность действий и уточнений между экземплярами logger, JSON-контракт C, резервирование бюджета, тариф без номера лота, status action из реально выданного ответа, manifest и HTTP-доставка файлов виджета. Это не браузерная приёмка и не прохождение общего release-gate.

Из 13 новых расхождений 11 ожидают закрытые сценарии при гостевом запросе: payment methods/accounting documents, штраф, основания отказа, закрытые сведения сотрудника, пропавший лот. Их нельзя устранять восстановлением обхода доступа; необходим отдельный пересмотр ожидаемого поведения и роли запроса. Исходные контрольные метки не изменены.

Ещё два случая — `подключить премиум` и `шаблон возврата`: маршрут сохраняется, но произвольные текстовые исключения больше не обходят проверку, поэтому возвращается более общий опубликованный контракт. Это реальная потеря адресности ответа, а не успешная регрессия. До выпуска нужны подтверждённые управляемые варианты ответа/служебные фразы; нельзя объявлять прежний Python-текст утверждённым только ради прохождения теста.

Среди подтверждённых исходных падений остаются несовпадения старых routing cases, несинхронный development dataset, условия старого офисного ответа и review queue, в которой `property.overview` пересекается с активным ID. Пакет их не скрывает, не снижает пороги старых отчётов и не правит предметные факты без отдельной публикации.

## Условия остановки и оставшаяся работа

Если B не улучшает ответы и увеличивает массовые уточнения, он остаётся экспериментом. Возврат маршрута — `ROUTING_ARCHITECTURE=control`, `LLM_UNDERSTANDING_ENABLED=false`; удаления таблиц или отката истории не требуется. Проверки доступа и происхождения ответа при этом сохраняются.

На момент завершения этого пакета до выпуска оставались: успешный инженерный отбор, полное состояние цели/сущностей/второго намерения, свободные follow-up, адресная сборка фактов, экспертный пересмотр просроченных знаний, контракты status API, доставка с подтверждением и идемпотентностью, общий deadline при перегрузке, независимые 500 одиночных и 100 двухходовых обращений, минимум 1000 **новых реальных** shadow-событий и ступенчатый rollout. Эти данные, внешние контракты и экспертные решения не заменяются сгенерированными здесь материалами.

По последующему указанию пользователя реализован отдельный экспериментальный слой состояния диалога: [этап 3 и его свежая проверка](dialogue-state-implementation-2026-09-04.md). Это не меняет приведённые выше результаты этапов 0–2 и не продвигает scorer B.

Расширение генерации или бизнес-интеграций до подтверждения выбора сценария не выполняется: это условие остановки исходного плана, а не разрешение выпуска непрошедшего кандидата.
