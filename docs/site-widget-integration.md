# Интеграция чат-виджета MIGTORG на migtorg.com

## 1. Назначение документа

Документ предназначен для frontend-, backend- и DevOps-команд MIGTORG и описывает подключение существующего чат-виджета к `migtorg.com`.

Архитектура интеграции:

```text
migtorg.com
  -> загружает widget.js и style.css
  -> передает контекст страницы и пользователя
  -> виджет обращается к chatbot backend по HTTPS
  -> backend формирует ответы, хранит историю и создает обращения
```

На стороне сайта не должны размещаться база знаний, правила ответов, ключи LLM, SMTP-реквизиты или логика создания обращений.

## 2. Компоненты

| Компонент | Назначение | Расположение |
|---|---|---|
| `widget.js` | Создает интерфейс чата и вызывает API | `frontend/chat-widget/widget.js` |
| `style.css` | Стили интерфейса | `frontend/chat-widget/style.css` |
| Chatbot backend | Ответы, история, feedback и обращения | FastAPI-приложение |
| Demo-страница | Локальная проверка виджета | `frontend/chat-widget/index.html` |

Backend публикует готовые файлы по адресам:

```text
https://CHAT_BACKEND_URL/widget/widget.js
https://CHAT_BACKEND_URL/widget/style.css
```

Адрес backend для production должен быть согласован до начала интеграции. Все обращения выполняются только по HTTPS.

## 3. Минимальное подключение

Разместить код перед закрывающим тегом `</body>` на страницах, где должен отображаться чат:

```html
<script>
  window.MIGTORG_CHAT_API_BASE = "https://CHAT_BACKEND_URL";

  window.MIGTORG_CHAT_CONTEXT = {
    is_authorized: false,
    user_id: null,
    page_type: "public_site",
    lot_id: null,
    user_email: null,
    user_phone: null
  };
</script>

<script src="https://CHAT_BACKEND_URL/widget/widget.js"></script>
```

`widget.js` самостоятельно:

- добавляет HTML-разметку чата в `document.body`;
- загружает `style.css` из той же директории, что и скрипт;
- создает и сохраняет `session_id` в `localStorage` под ключом `migtorg_chat_session_id`;
- отправляет запросы в chatbot backend.

Настройки `MIGTORG_CHAT_API_BASE` и `MIGTORG_CHAT_CONTEXT` должны быть объявлены **до** подключения `widget.js`. Не следует добавлять атрибут `async`. При использовании `defer` настройки и скрипт должны сохранять указанный порядок.

## 4. Контекст страницы и пользователя

Формат `window.MIGTORG_CHAT_CONTEXT`:

```javascript
window.MIGTORG_CHAT_CONTEXT = {
  is_authorized: true,
  user_id: "12345",
  page_type: "lot_card",
  lot_id: "98765",
  user_email: "user@example.com",
  user_phone: "+79990000000"
};
```

| Поле | Тип | Обязательно | Описание |
|---|---|---:|---|
| `is_authorized` | boolean | да | Признак авторизации для выбора сценария ответа |
| `user_id` | string/null | нет | Внутренний идентификатор пользователя |
| `page_type` | string | да | Тип текущей страницы |
| `lot_id` | string/null | для карточки лота | Идентификатор текущего лота |
| `user_email` | string/null | нет | Контакт для формы обращения |
| `user_phone` | string/null | нет | Контакт для формы обращения |

Поддерживаемые значения `page_type`:

| Значение | Страница |
|---|---|
| `public_site` | Публичная страница или неизвестный тип |
| `registration` | Регистрация |
| `login` | Вход |
| `tariffs` | Тарифы |
| `lot_catalog` | Каталог лотов |
| `lot_card` | Карточка лота |
| `balance` | Баланс |
| `payments` | Платежи |
| `won_lots` | Выигранные лоты |
| `transferred_lots` | Переданные лоты |
| `support` | Поддержка |

Если страница не соответствует перечисленным типам, передается `public_site`.

### Примеры

Гость на публичной странице:

```javascript
window.MIGTORG_CHAT_CONTEXT = {
  is_authorized: false,
  user_id: null,
  page_type: "public_site",
  lot_id: null,
  user_email: null,
  user_phone: null
};
```

Авторизованный пользователь в карточке лота:

```javascript
window.MIGTORG_CHAT_CONTEXT = {
  is_authorized: true,
  user_id: "12345",
  page_type: "lot_card",
  lot_id: "98765",
  user_email: "user@example.com",
  user_phone: null
};
```

### SPA и изменение состояния

Текущая версия виджета читает `MIGTORG_CHAT_CONTEXT` один раз при загрузке `widget.js`. Если сайт работает как SPA и после загрузки меняет маршрут, лот или состояние авторизации, необходимо либо перезагрузить виджет/страницу, либо доработать виджет для динамического обновления контекста. Это решение должно быть принято до production-интеграции.

## 5. Сетевые требования

Chatbot backend должен разрешать CORS только для согласованных origin сайта:

```env
CORS_ALLOWED_ORIGINS=https://migtorg.com,https://www.migtorg.com
```

Если используется отдельный staging-домен, его origin добавляется отдельным значением. Origin включает схему и домен, но не путь.

На стороне инфраструктуры необходимо:

- опубликовать backend и файлы виджета по HTTPS;
- обеспечить доступность `POST`-запросов с JSON;
- не кэшировать API-ответы;
- включить версионирование или контролируемое кэширование `widget.js` и `style.css`;
- добавить домен chatbot backend в CSP сайта.

Пример минимальных дополнений CSP, если backend расположен на `chat.example.com`:

```text
script-src ... https://chat.example.com;
style-src  ... https://chat.example.com;
connect-src ... https://chat.example.com;
```

Фактическую политику CSP следует объединить с действующей политикой сайта, а не заменять приведенным примером.

## 6. Используемые API

Виджет вызывает следующие публичные endpoint'ы:

| Метод и путь | Назначение |
|---|---|
| `GET /health` | Проверка доступности backend |
| `POST /api/chat/message` | Отправка сообщения |
| `POST /api/chat/ticket` | Создание обращения |
| `POST /api/chat/feedback` | Отправка оценки ответа |
| `GET /api/chat/history/{session_id}` | Получение истории, если потребуется сайту |

Endpoint `POST /chat` является устаревшим и для новой интеграции не используется.

Проверка backend:

```bash
curl https://CHAT_BACKEND_URL/health
```

Минимальный ожидаемый признак успешного ответа:

```json
{
  "status": "ok"
}
```

## 7. Безопасность и персональные данные

### Ограничение текущей модели авторизации

`MIGTORG_CHAT_CONTEXT` формируется в браузере, поэтому пользователь технически может изменить `is_authorized`, `user_id`, `lot_id`, email и телефон. Текущий backend использует этот контекст для выбора сценария ответа, но не подтверждает его через сессию сайта.

Следовательно:

- контекст нельзя считать доказательством авторизации;
- по нему нельзя раскрывать баланс, платежи, документы, контактные данные или иные персональные сведения;
- backend не должен выполнять операции с аккаунтом или лотом только на основании этих значений;
- для персонализированных данных нужна отдельная server-to-server интеграция или подписанный краткоживущий токен, проверяемый chatbot backend.

До реализации защищенной авторизации виджет должен оставаться справочным и переводить вопросы, требующие проверки учетной записи, в обращение к сотруднику.

### Передача контактов

`user_email` и `user_phone` следует передавать только после согласования с ответственным за обработку персональных данных. Если предварительная передача не разрешена, нужно передавать `null`: пользователь сможет ввести контакт непосредственно в форме обращения.

В frontend запрещено размещать:

- API-ключи LLM-провайдеров;
- SMTP-пароли;
- токены внутренних отчетов;
- служебные ключи интеграций с Bitrix, Telegram и другими системами.

## 8. Порядок внедрения

1. Согласовать production- и staging-адреса chatbot backend.
2. Проверить конфигурацию командой `python -m backend.tools.check_production_readiness --env-file .env.production --strict`.
3. Развернуть backend на staging и проверить `/health`.
4. Ограничить CORS staging- и production-origin сайта.
5. Добавить chatbot-домен в CSP staging-сайта.
6. Определить соответствие маршрутов сайта значениям `page_type`.
7. Подключить настройки и `widget.js` на staging.
8. Проверить гостевой и авторизованный контекст.
9. Проверить карточку лота с корректным `lot_id`.
10. Проверить создание обращения и доставку обращения сотрудникам.
11. Выполнить приемочное тестирование на desktop и mobile.
12. Зафиксировать версии backend и файлов виджета.
13. Повторить конфигурацию для production и провести smoke-тест.

## 9. Приемочные проверки на staging

- Виджет появляется на нужных страницах и не перекрывает критические элементы сайта.
- Виджет открывается и закрывается на desktop и mobile.
- Сообщение успешно отправляется, ответ отображается один раз.
- После обновления страницы сохраняется `session_id`.
- Гость получает роль `guest`.
- Авторизованный пользователь получает роль `authorized`, но персональные данные не раскрываются без защищенной интеграции.
- На карточке лота передается правильный `lot_id`.
- Форма обращения требует контакт и описание.
- Созданное обращение получает номер и действительно поступает в настроенный канал поддержки.
- Ссылки на документы открываются по HTTPS.
- При недоступном backend виджет показывает понятную ошибку и не ломает страницу сайта.
- В консоли браузера нет ошибок CORS, CSP и загрузки ресурсов.
- На странице и в исходном коде отсутствуют секретные ключи.
- Demo-панель управления не отображается на production-страницах.

## 10. Выпуск и откат

Перед выпуском необходимо зафиксировать:

- URL и версию backend;
- URL/версию `widget.js` и `style.css`;
- список разрешенных CORS-origin;
- владельца мониторинга backend;
- канал получения обращений;
- ответственного за отключение виджета.

Самый быстрый откат на стороне сайта — удалить или временно отключить тег подключения `widget.js`. Это не затрагивает основную функциональность сайта. После отката следует проверить, что страница не продолжает загружать CSS или выполнять запросы к chatbot backend.

## 11. Границы ответственности

Команда сайта отвечает за:

- подключение виджета;
- корректный контекст страницы;
- CSP и совместимость с интерфейсом сайта;
- включение/отключение виджета при выпуске и откате.

Команда chatbot backend отвечает за:

- доступность API и статических файлов;
- CORS;
- ответы и безопасность сценариев;
- хранение истории;
- создание и доставку обращений;
- логи, мониторинг и восстановление сервиса.

Совместно согласовываются обработка персональных данных, защищенная авторизация, staging-приемка и production-запуск.
