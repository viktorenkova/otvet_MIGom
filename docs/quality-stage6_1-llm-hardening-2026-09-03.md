# Этап 6.1 — безопасное подключение LLM к формулировке ответа

Дата фиксации: 3 сентября 2026 года.

## Результат

Инженерная часть этапа реализована. LLM остаётся только редактором текста уже выбранной карточки БЗ: она не выбирает тему, не видит соседние карточки и не может менять утверждённые факты. При отсутствии контракта, невысокой уверенности маршрута, уточнении, safety-ответе, создании обращения, ошибке, timeout, открытом circuit breaker или превышении бюджета пользователь получает детерминированный ответ БЗ.

Это уменьшает риск ухудшить достигнутое качество маршрутизации ради более естественной формулировки. Цель 8/10 по теме и корректности по-прежнему измеряется на полном ответе бота, а не по красоте текста LLM.

## Что реализовано

1. Fail-closed допуск только для high-confidence сценария с валидным answer contract.
2. Prompt из approved template и разрешённых fact IDs после единого маскирования ПД.
3. Verifier для новых фактов, чисел, контактов, prompt injection, обещаний и смысловых инверсий; при сомнении используется baseline.
4. Маскирование телефонов, email, URL, Telegram, обфусцированных контактов, VIN, госномеров, ФИО, адресов и идентификаторов.
5. Стоимость по входным/выходным токенам, дневной и месячный hard stop, порог предупреждения, раздельная среда.
6. Общий deadline основного и резервного вызова, ограничение выходных токенов и параллельности, circuit breaker.
7. Агрегированная серверная телеметрия без исходного текста: provider/model, latency, tokens, cost, решение verifier, fallback и корреляционный ID.
8. Fail-fast проверка endpoint, ключа, тарифов, бюджетов и допустимой ступени rollout.
9. Shadow-runner на 200–500 запросах с маскированным пакетом независимой оценки.
10. Стабильные пользовательские когорты `0/5/25/50/100` и формальная rollback policy в `configs/llm_answer_rollout_policy.json`.

## Проверки

- 29 целевых тестов LLM, verifier, privacy, manifest и production readiness прошли.
- 3 интеграционных сценария, выявившие позднюю инициализацию признака уточнения, исправлены и прошли повторно.
- Полный regression suite дважды дошёл дальше прежней точки падения на 11%, но не завершён: отдельные deployed-chat параметры после принудительной очистки dense-cache вычисляются аномально долго. Найденная функциональная регрессия исправлена и подтверждена отдельными интеграционными тестами; полный зелёный suite остаётся обязательным gate до пользовательского rollout.
- API-ключ не добавлялся в файлы, команды, отчёты или Git.

## Что ещё не является закрытым gate

Реальный Qwen-shadow не выполнен. Для него оператор локально задаёт backend-секрет и актуальные цены входных/выходных токенов, оставляя `LLM_ROLLOUT_PERCENTAGE=0`, затем запускает 200–500 запросов. Независимый проверяющий сравнивает только маскированные LLM-кандидаты с baseline.

До пользовательского включения одновременно требуются:

- 0 критических новых или искажённых фактов;
- 0 обнаруживаемых ПД;
- корректность не ниже baseline, понятность и релевантность выше baseline;
- 100% безопасный fallback при ошибках провайдера;
- приемлемые p95, error rate и стоимость;
- зелёный полный regression suite.

Поэтому текущий безопасный режим — `LLM_ROLLOUT_PERCENTAGE=0`. После успешного shadow переход выполняется последовательно: 5% → 25% → 50% → 100%, с возвратом на 0% при любом rollback-триггере.

## Внеочередная задача — скорость первого ответа

3 сентября 2026 года при локальном запуске была выявлена задержка до 60+ секунд на отдельных вопросах, например о документах. Stack trace показал, что это не LLM и не сеть: при первом обращении строился `routing_v3`, а нормализация каждого проверенного текста БЗ заново перебирала доменный словарь через Damerau–Levenshtein.

Исправление выполнено до продолжения этапа: результат коррекции одного токена кэшируется, а при построении индекса проверенные документы БЗ больше не проходят fuzzy-коррекцию; она сохраняется для пользовательского текста. Целевые маршрутизационные тесты прошли (`13 passed`). Холодная сборка маршрутизатора сократилась с примерно 75 до 40 секунд, а проблемный запрос после прогрева обрабатывается за 0,195 секунды. В штатном запуске этот расчёт выполняется до открытия API; пользователь не должен ждать его в сообщении.
