# Этап 3: понимание запроса и состояние диалога

Статус: экспериментальная реализация; по умолчанию выключена. Продолжение работ по отдельному указанию пользователя после эксперимента этапов 0–2. Не означает продвижения не прошедшего отбор scorer B или разрешения выпуска.

## Что изменилось

Путь с `DIALOGUE_STATE_ENABLED=true`:

`сообщение → проверенный контекст → захват сессии в SQLite → проверка предыдущего хода → структура запроса и переход состояния → существующая маршрутизация → ответ → совместное сохранение ответа и состояния → освобождение сессии`.

Внутренние модели `QueryUnderstanding`, `DialogueState` и `DialogueTurn` отделяют цель, объекты, операции, состояния, участника, сущности, фоновые события, отрицания, неизвестные поля и дополнительные вопросы. Словарь и исходный классификатор взяты из проекта; новая предметная БЗ не создавалась. Локальные правила интерпретации пока ограничены, в частности не являются полноценным семантическим разбором всех отрицаний и неоднозначностей.

В SQLite добавлены таблицы `dialogue_states` и `dialogue_leases`. Состояние хранит активную задачу, сущности, выбранный сценарий, варианты и ожидаемое поле уточнения, ожидающее действие, очередь вопросов, предыдущий ответ и версию. Рабочие процессы читают его из общей БД. История и обращения не удаляются.

Для одной сессии одновременно выполняется один ход. Атомарный захват через `BEGIN IMMEDIATE` удерживает логическую аренду, а не открытую транзакцию на всё время ответа. Конкурирующий запрос получает HTTP 409 `dialogue_turn_in_progress`. Аренда истекает через 120 секунд для восстановления после аварии; истёкший владелец не может сохранить поверх нового состояния и получает `dialogue_turn_expired`. Это механизм восстановления, **не** общий deadline обработки. Долгие вызовы и их побочные эффекты остаются предметом этапа надёжности.

`conversation_turn_id` теперь проверяется и для свободных реплик. Необязательный `state_version` дополнительно защищает от устаревшего состояния; конфликт возвращает 409 `stale_conversation_turn`. Старые клиенты без этих полей продолжают последовательную работу по `session_id`. Виджет уже отправляет `conversation_turn_id`; обязательных изменений его протокола не потребовалось.

## Поведение

- Короткое продолжение получает предмет из активной задачи; для поиска строится отдельная реплика с предметом, без склейки всей истории.
- Явная смена темы очищает текущие сущности и ожидание действия. Повтор различается с новой задачей.
- Номер лота может быть сообщён, исправлен или отвергнут. Исправление заменяет прежний идентификатор и в поисковом запросе. Голый номер разрешает только ранее ожидаемое поле.
- После запроса номера для выбранного status action следующее сообщение продолжает это действие. Сохраняются проверки его выдачи в предыдущем ответе, текущей роли, подписи и scopes. Состояние никогда не восстанавливает доверенную личность или токен.
- Смена пользователя/роли сбрасывает активный контекст. Переход через выключенную экспериментальную ветку также инвалидирует старое состояние при повторном включении.
- Свободный выбор из предложенных вариантов разрешается только при единственном различительном совпадении; ограничения доступа проверяются повторно. Прежний выбор категории письменного обращения сохранён.
- Дополнительный вопрос, включая просьбу перезвонить после предметного вопроса, сохраняется отдельно. Поле ответа `pending_requests` и служебная фраза показывают очередь; команда «следующий вопрос» обрабатывает следующий элемент. Это сохранение вопроса, а не заказ звонка или доставка обращения.
- Пунктуация одиночного запроса сохраняется. Вопросительный знак сам по себе не доказывает наличие второй задачи: для такого разделения требуются разные распознанные намерения. Явные разделители «и ещё» и точка с запятой также поддерживаются. Распознавание независимых вопросов пока ограничено этой локальной эвристикой.
- Несодержательное продолжение после уточнения либо повторно неразрешённое уточнение приводит к предложению письменной ручной проверки. Обращение автоматически не создаётся; история и собранные данные сохраняются. Safety-ответ сбрасывает активную задачу.

## Проверки и воспроизведение

Новые механизмные тесты: `tests/test_dialogue_state.py`. Они включают HTTP-конфликты версий, конкурентные экземпляры SQLite, потерю аренды, перезапуск DAO, смену личности, статусы с недостающим номером, ограничения гостя, очередь вопросов и существующий выбор категории обращения. Искусственные значения номеров используются только как проверка механизма, не как независимые пользовательские данные.

Сквозной evaluator: `python -B -m backend.tools.evaluate_dialogue_state`. Он изолирует БД, отключает внешние модели, доставку и реальные status API, прогревает существующий локальный поиск. Сравнивает флаг off/on на контрольных 270 одиночных обращениях, пяти исходных диалогах и трёх явно отмеченных производных случаях со свободным продолжением. Для одиночных запросов сравнивает прямой вызов и HTTP; для каждого хода HTTP заново создаёт DAO. Применяется прежний проверяемый overlay, исходные метки не редактируются.

Итог сохраняется в `reports/dialogue-state-evaluation.json`; подробные ответы и трассы — в `.work/dialogue-state-details.json`. Manifest включает флаг состояния, хеши приложения, evaluator, знаний и фактическую доступность dense-канала. Проверки маршрута, resolution и текстовых маркеров обозначены как автоматические; экспертная смысловая оценка не подменяется ими.

Первый прогон обнаружил скрытую равным суммарным счётом регрессию `widget-068`: удаление завершающей точки меняло маршрут `transfer.not_confirmed` на `pickup.receive_lot`. Исправлена причина — непреднамеренное преобразование одиночного поискового запроса. Также устранено автоматическое разделение связанных и риторических фраз только по вопросительному знаку. Метки корпуса и факты БЗ при этих исправлениях не менялись. Первоначальный отчёт сохранён в `.work/dialogue-initial-evaluation.json` для диагностики; итоговый отчёт получает повторный свежий прогон.

## Результат окончательного сквозного прогона

| Автоматическая проверка | Слой выключен | Слой включён |
|---|---:|---:|
| Успешные проверки ответа | 212/270 (78,52%) | 213/270 (78,89%) |
| Правильный маршрут | 217/270 | 218/270 |
| Уверенные ошибки ответа среди high | 40/236 (16,95%) | 39/236 (16,53%) |
| Исходные диалоги | 5/5 | 5/5 |
| Производные свободные продолжения | 2/3 | 3/3 |
| p95 локального HTTP-пути после прогрева | 865,24 мс | 596,96 мс |

В окончательном прогоне единственное изменение маршрута/успешности одиночного ответа — улучшение `widget-075`: `pickup.receive_lot → pickup.access_issuer`. Потерь ранее успешных случаев нет. `widget-068` после исправления снова проходит. Существующие ошибки в остальных случаях сохранены в полном отчёте; суммарный прирост недостаточен для release-gate.

Свободное продолжение «а как его подключить?» после ответа о премиальном тарифе теперь получает `tariff.connect`; раньше возвращалось `out_of_scope`. Это производный разработческий пример из исходного диалога `dlg-premium-action`, а не новая независимая разметка.

Проверены 540 пар прямого вызова и HTTP для одиночных запросов — расхождений нет. Хеши приложения, знаний и evaluator неизменны во время прогона; локальный dense-канал доступен. Внешние LLM, доставка и бизнес-API не использовались. SQLite DAO пересоздавался перед каждым HTTP-ходом.

Замер включает локальный TestClient и пересоздание DAO, исключает прогрев модели; он не измеряет сеть, реальный браузер или конкурентную производственную нагрузку. В этом сопоставлении дополнительной деградации p95 нет, но его нельзя приравнивать к историческому direct-only baseline этапов 0–2 или считать гарантией производственного SLA.

Окончательный профильный suite: **66 passed**, один тест структуры исторического отчёта исключён через `-m 'not report_snapshot'`. Включены 30 проверок нового слоя, архитектурные границы, manifest, контракты ответа, доставка файлов виджета через HTTP и scorer bundle. JUnit: `.work/dialogue-final-tests.xml`. Это проверка текущего кода; ручная браузерная проверка и полный suite не заявляются. Ранее зафиксированные 43 падения полного suite этапов 0–2 этим результатом не аннулируются и не считаются исправленными.

## Ограничения и откат

Откат: `DIALOGUE_STATE_ENABLED=false` и перезапуск приложения. Данные остаются в SQLite. Параметры `ROUTING_ARCHITECTURE` и `LLM_UNDERSTANDING_ENABLED` независимы; значения по умолчанию остаются `control` и `false`. Пользовательская LLM-переформулировка в архитектурном эксперименте отключена.

Этот этап добавляет механизм контекста, но не устраняет установленные ранее ошибки единого scorer, не проверяет семантическую корректность всех ответов и не реализует адресную сборку фактов этапа 4. Пять известных диалогов и три производных примера не подтверждают порог 85% на независимых 100 двухходовых диалогах. Полный release-gate, экспертная разметка, нагрузочные задержки, новые shadow-события и rollout остаются открытыми. Выпуск закрыт.
