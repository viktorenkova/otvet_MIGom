# Этап 5: бизнес-действия и надёжность

Дата: 2026-09-04. Основа — `2001e3d` (этап 4), отправлен в `origin/main`. Этот пакет продолжает согласованный план; знания, метки и правила выбора сценария не менялись. Реальные status API, SMTP и внешняя LLM не вызывались. Пакет не является разрешением выпуска.

## Реализованный механизм

### Статусы бизнес-объектов

Сохранена защищённая провайдерная граница и проверка действия из предыдущего ответа той же сессии. Тариф использует подтверждённого пользователя, остальные существующие status actions — номер лота; свободное продолжение с номером использует состояние диалога из этапа 3. Дополнительные бизнес-операции не добавлены.

`InternalApiStatusProvider` принимает только JSON-объект с непустым строковым `status`, строковым `description`, необязательным `freshness` и массивом строк `allowed_actions`. Лишние поля и неверные типы отклоняются. Ответ ограничен 64 KiB, status — 120 символами, description — 2000; freshness должен быть ISO-временем с часовым поясом. Это строгая версия существующей границы проекта, а не подтверждённый контракт действующей бизнес-системы.

Отдельные исходы: отсутствие доступа (401/403), отсутствие объекта (404), неизвестный статус, некорректная структура, ошибка сервиса и исчерпанное время. При неуспехе предлагается ручная проверка; обращение автоматически не создаётся. `received_at` означает получение ответа, `data_freshness` — только явно указанную источником свежесть. Время получения не подставляется вместо свежести.

API не может создавать произвольные кнопки: выдаются только действия текущего сценария из `allowed_actions`, затем применяется общая проверка роли. При отсутствии списка подтверждённых действий успешный status-ответ кнопок не добавляет.

### Создание и отправка обращения

Создание обращения и постановка в очередь выполняются одной SQLite-транзакцией. HTTP-обработчик больше не ждёт SMTP. Необязательный `idempotency_key` связывает повтор запроса в одной сессии с исходным обращением. Разные данные с тем же ключом возвращают HTTP 409. Для старых клиентов ключ вычисляется из полей запроса; одинаковое повторение возвращает прежний номер. Для намеренного нового обращения с теми же данными клиент должен передать новый ключ либо начать новую сессию.

Добавлены таблицы `ticket_requests`, `ticket_outbox`, `processing_slots`; история и обращения сохраняются. Состояния очереди:

| Состояние | Подтверждённое событие | Повтор |
|---|---|---|
| `saved` | Обращение сохранено, отправка выключена | Только явная постановка в очередь |
| `pending` | Ожидает отправителя | Автоматический захват |
| `sending` | Попытка закреплена за одним worker | Конкурирующий worker не отправляет |
| `accepted` | SMTP-сервер принял письмо | Не повторяется |
| `failed` | Подтверждённый отказ до принятия письма | Через 5 минут, максимум 5 попыток |
| `unknown` | Принятие письма нельзя подтвердить или исключить | Только ручная проверка |

**`accepted` не означает доставку в почтовый ящик или прочтение сотрудником.** Подтверждение фактической доставки отсутствует; в отчёте оно остаётся `null`. Старое поле `status=sent_email` сохраняется для совместимости, его точная интерпретация теперь доступна в `delivery`.

Worker получает запись под `BEGIN IMMEDIATE`, завершение проверяет токен владельца. У потерянного worker через две минуты попытка становится `unknown`; автоматическая повторная отправка запрещена, поскольку письмо могло уйти перед сбоем. Один и тот же ticket имеет стабильный Message-ID; сам по себе он не гарантирует дедупликацию у получателя. Тайм-аут или разрыв SMTP также не объявляется доказанным отказом. Старые `sent_email` импортируются как `accepted` без выдуманного времени принятия, старые неясные/ошибочные отправки — как `unknown`, остальные — как `saved`.

`POST /api/chat/ticket` и результат действия чата показывают реальное состояние очереди. Виджет использует это состояние в подтверждении и больше не обещает связь сотрудника по одному факту сохранения. Защищённый quality report содержит число обращений в каждом состоянии и до 100 ID для ручной проверки. Содержимое обращений этим дополнением не раскрывается.

### Время, перегрузка и бюджет

Внешние вызовы получают остаток общего пятисекундного бюджета с резервом на завершение; status API и LLM ограничены четырьмя секундами. После просроченного поиска обработчик возвращает низкоуверенное уточнение и не создаёт обращение. SQLite хранит общий лимит одновременно исполняемых запросов (`CHAT_MAX_CONCURRENCY=8`); превышение возвращает HTTP 503 и `Retry-After: 2`. Освобождение выполняется в `finally`, потерянные разрешения истекают через две минуты.

Лимит времени **кооперативный**: синхронное локальное вычисление, ожидание SQLite и последовательные операции сокета нельзя гарантированно остановить на пятой секунде. После истечения двухминутной аренды зависший процесс также может ещё работать. Поэтому это защита от обычной перегрузки, не доказательство строгого SLA при зависании. Нужны нагрузочная проверка и при необходимости изолированное прерываемое исполнение. Прогрев индексов остаётся в lifespan приложения.

LLM-переформулировка в архитектурном эксперименте выключена. Для её будущего включения HTTP-путь теперь резервирует оценочную стоимость в SQLite до вызова, учитывая параллельные запросы. Резерв удерживается до регистрации результата; второй модельный fallback выключен, чтобы не создавать незарезервированный вызов. Нулевая неизвестная цена внешнего провайдера не разрешает запрос. Оценка не заменяет сверку фактического биллинга, особенно после сетевого сбоя; прямые вспомогательные вызовы генератора вне HTTP-контекста не являются обслуживающим контуром.

## Эксплуатация и откат

Доставка требует **отдельно запущенного отправителя** с той же SQLite и подтверждёнными SMTP-настройками. Без него `pending` остаётся ожидающим. Он не запускается автоматически ни из чата, ни при миграции. Разовая обработка: `python -B -m backend.tools.deliver_ticket_outbox`; постоянный опрос: та же команда с `--watch --interval 5`. Эти команды реально отправляют письма при настроенной интеграции и в рамках этой работы не выполнялись. CLI отказывается запускать отправку при выключенном email или отсутствии SMTP_HOST.

Существующий защищённый `POST /api/internal/tickets/retry-due` использует ту же очередь (до 20 записей за вызов). Ключи `sent`/`failed` сохранены, добавлен `unknown`; `sent` здесь означает принятие SMTP. Для неизвестных исходов сначала требуется проверка почтового сервера/сотрудника. Автоматического принудительного сброса `unknown` нет.

До включения доставки нужен операторский запуск worker и наблюдение за очередью. Реальные бизнес-API подключаются только после подтверждения схем, реквизитов, семантики статусов и свежести; пока остаётся справочный режим с ручной проверкой. Доставка в ящик и эксплуатационное развёртывание worker не подтверждены.

Откат к `2001e3d` не требует удаления таблиц. Перед откатом остановить новый отправитель и выключить email, сверить `pending`/`sending`/`unknown`; старый синхронный отправитель и новый worker не должны работать одновременно. Автоматического отката истории или повторной отправки накопленной очереди нет. Флаги диалога, сборки ответа и маршрутизации независимы, их значения по умолчанию не повышались до экспериментальных веток.

Профильный suite: 111 passed, 1 deselected (`report_snapshot`); после добавления проверки просроченного поиска и расширения проверки допустимых API-действий — ещё 2 passed (один повторный тест, всего 112 различных тестов). Проверены конкурирующие SQLite-отправители, повтор HTTP-запроса, конфликт ключа, миграция, сбои SMTP, потеря worker, недопустимая структура status API, роли, продолжения диалога, источники ответа, бюджет и перегрузка. Внешние провайдеры заменены контролируемыми подставными реализациями.

JUnit: `.work/reliability-tests.xml`, `.work/reliability-final-tests.xml`. JavaScript прошёл `node --check frontend/chat-widget/widget.js`; выдача файлов виджета проверена через HTTP. Реальная браузерная проверка и полный suite в этом пакете не выполнялись; ранее известные падения полного suite не объявляются устранёнными.

Свежая регрессия: `python -B -m backend.tools.evaluate_business_reliability`. Отдельная временная БД, прежний корпус 270 и прежний проверенный overlay, прогрев, контрольная маршрутизация, включённые экспериментальные диалог и сборка ответа, выключенные внешние сервисы. Отчёт: `reports/business-reliability-evaluation.json`; детали: `.work/business-reliability-details.json`. Это автоматические проверки меток/маркеров и локальная последовательная задержка, не независимая семантическая приёмка, нагрузочный тест или разрешение выпуска.

Свежий результат: **213/270** автоматических успешных ответов, **218/270** правильных маршрутов, **39/236** уверенно неверных ответов среди high (16,53%). По этим метрикам изменений относительно этапа 4 нет; качество остаётся ниже release-gate. Во всех **14 HTTP-пробах** ответ, маршрут, resolution, действия и документы совпали с прямым вызовом. Знания и корпус совпадают с предыдущим отчётом; хеши bundle не изменились во время прогона.

Локальный p95 после прогрева — **736,82 мс**. В историческом прогоне этапа 4 для `assembly_on` было около 433 мс; нынешний результат выше. Это разные запуски, причём исторический `assembly_on` шёл после полного прохода `assembly_off`, поэтому сравнение не изолирует накладные расходы новой реализации и состояние кэшей. **Условие ухудшения не более 10% не подтверждено**, хотя измеренная локальная задержка ниже пяти секунд. Перед включением нужен сопоставимый парный benchmark и нагрузочная проверка.

Итог поставки: механизм статусов, очереди, идемпотентности и ограничения ресурсов реализован и прошёл профильные проверки. Полная эксплуатационная приёмка этапа 5 остаётся открытой: реальные контракты API, SMTP и доставка в ящик, запуск worker, сопоставимая производительность и обязательные проверки перед выпуском отсутствуют.
