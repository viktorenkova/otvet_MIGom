# Аудит БЗ, маршрутизации и LLM чат-бота MIGTORG

Дата проверки: 13 августа 2026 года
Проверяемый dev API: `https://chat.migtorg.com/api/chat/message`
Итоговый статус: **к выпуску в production не готов**

## 1. Краткий вывод

Цель «не менее 8 попаданий из 10» не достигнута ни развернутой dev-версией, ни текущим локальным кодом.

| Показатель | Dev с Qwen | Текущий локальный код без LLM | Цель |
|---|---:|---:|---:|
| Запросы с ответом API | 160/160 — 100% | 160/160 — 100% | 100% |
| Верный сценарий | 73/160 — 45,62% | 88/160 — 55,00% | ≥ 85% |
| Верный сценарий + intent | 70/160 — 43,75% | 85/160 — 53,12% | ≥ 85% |
| Полностью приемлемый ответ | **56/160 — 35,00%** | **73/160 — 45,62%** | **≥ 80%** |
| Полностью пройденные диалоги | 1/5 — 20% | 2/5 — 40% | ≥ 80% |
| Запрещенного содержания нет | 156/160 — 97,50% | 159/160 — 99,38% | 100% |

Главный вывод: корневая проблема находится прежде всего **до LLM**. Развернутая версия вызвала `qwen-plus` только в 40 из 160 запросов (25%). В остальных 120 случаях ответ сформирован шаблоном: LLM не вызывается при уточнениях и эскалациях и не может исправить уже ошибочно выбранный сценарий.

Даже среди 40 вызовов Qwen верный маршрут был только у 20. При верном маршруте 16 из 20 ответов прошли все критерии. Это означает:

- Qwen способен приемлемо переформулировать правильный контекст;
- Qwen не исправляет ошибку маршрутизатора и уверенно оформляет нерелевантную статью;
- текущие ограничения генерации недостаточны: в трех корректно маршрутизированных ответах модель сохранила запрещенную лишнюю информацию или имя сотрудника;
- сравнение dev и local нельзя считать чистым A/B-тестом LLM, потому что на dev развернут более старый код.

До исправления маршрутизации, деплойного рассинхрона и обязательных content-guard выпускать эту версию нельзя.

## 2. Что и как проверялось

Создан независимый набор из **160 одиночных запросов** и **5 двухшаговых диалогов**. Ни одна из 160 формулировок не совпадает после нормализации с 935 `positive_examples` текущей БЗ.

Состав одиночного набора:

| Класс | Количество |
|---|---:|
| Опечатки | 26 |
| Перестановленные слова | 26 |
| Разные словоформы и названия действий | 25 |
| Перестановленные буквы | 23 |
| Естественные разговорные формулировки | 22 |
| Варианты названий страховых | 12 |
| Запросы с именами сотрудников | 5 |
| Вне тематики | 5 |
| Грубые, но относящиеся к MIGTORG | 5 |
| Повторенный пользователем текст | 5 |
| Неоднозначные запросы | 4 |
| Разговорные сокращения | 2 |

Страховые проверялись в полных фразах после выигрыша или передачи лота: РЕСО, АльфаСтрахование, Т-Страхование, Ингосстрах, Росгосстрах, ВСК, Согласие, Ренессанс, СберСтрахование, Совкомбанк Страхование, Зетта и Югория, а также варианты с опечатками и разговорные «ресо гасится», «альфа ушла в тишину».

Каждый запрос прошел полный `process_chat_message` локально и реальный публичный dev API. Для dev использовались отдельные сессии с префиксом `kb-audit`; контакты и согласие на обращение не передавались, поэтому реальные тикеты не создавались.

Двухшаговые цепочки проверяли:

1. общий запрос адреса → выбор визита в офис;
2. общий возврат → выбор подачи заявления;
3. описание Премиума → кнопка подключения;
4. инструкция по ставке → кнопка «ставка не появилась»;
5. новая тема о ставке после уточнения по возврату.

### Критерии оценки

- `route_hit`: попали в один из допустимых `scenario_id` и допустимый `intent`;
- `answer_hit`: верный маршрут, ожидаемый тип реакции, обязательные смысловые маркеры, отсутствие запрещенного содержания и отсутствие ненужного уточнения;
- `quality_pass`: `answer_hit`, нет повторенной фразы, длина ответа не больше 900 символов;
- для неоднозначных запросов правильным считалось уточнение, а не догадка;
- для запроса по сотруднику правильным считался ответ без любого повторения имени;
- для подключения Премиума запрещена нерелевантная информация о демо-доступе;
- для общего адреса запрещена немедленная выдача адреса офиса.

Это строгая бизнес-приемка, а не оценка «ответ хоть как-то связан с темой».

### 3.3. Страховые и отсутствие ответа

Это самый наглядный деплойный регресс.

- Dev не попал в нужный сценарий ни разу: **0/20**.
- Текущий локальный код с новым `transfer.seller_no_response` попал: **11/20**.
- Оставшиеся локальные промахи показывают, что одного нового сценария недостаточно: нужны нормализация названий, опечаток и более устойчивые признаки «выигрыш/передача + нет ответа».

На dev запросы о молчащей страховой уходили в:

- задержку документов — 4 раза;
- карточку лота — 3 раза;
- невидимую ставку;
- местонахождение лота;
- правила ОСАГО;
- регистрацию автомобиля после покупки;
- общие уточнения или `out_of_scope`.

Примеры:

| Запрос | Фактический результат dev |
|---|---|
| «после победы РЕСО перестали выходить на связь» | `documents.preparation_delay` |
| «т страхование не отвечает по переданному лоту» | `lot.card_information` |
| «ингосстрах пропал после завершения торгов» | `bid.not_visible` |
| «росгосстрах игнорирует мои письма по авто» | `lot.location`; Qwen сообщает про адрес стоянки |
| «совкомбанк страхование потерялись после торгов» | `insurance.osago_rules`; Qwen объясняет правила ОСАГО |

Это не ошибка стилистики LLM: модель получила неверный контекст и аккуратно сформулировала неверный ответ.

### 3.4. Уточнения и полные диалоги

На dev полностью прошел только диалог по возврату — **1 из 5**.

- Общий адрес `«подскажите ваш адрес»` на dev ушел в `out_of_scope` и показал общее меню вместо уточнения цели. Второй шаг «офис» поэтому невозможно выбрать.
- `«что дает премиальный тариф»` выбрал `tariff.one_time`, а не `tariff.premium`.
- `«как поставить цену на автомобиль»` также выбрал `tariff.one_time`; кнопки «ставка не появилась» в ответе не было.
- После `«вернуть»` бот сразу эскалировал `refund.eligibility`, а следующий самостоятельный вопрос о ставке превратил в новое уточнение вместо `bid.place`.

В текущем локальном коде цепочка адреса уже проходит, но полностью успешны только 2 из 5 диалогов. Значит, исправления из рабочей копии полезны, но до требуемой устойчивости далеко.

### 3.5. Запрещенные имена и лишняя информация

На dev обнаружены четыре нарушения проверяемых бизнес-ограничений:

1. `«как подкючить премиум тарифф»` — добавлена информация «для демо-доступа достаточно…»;
2. `«нужна инструкция по подключению премиального доступа»` — та же лишняя информация;
3. `«возврат»` — вместо уточнения сразу предложено нажать «Создать обращение»;
4. `«дайте прямой номер Михаила»` — ответ повторил имя «Михаила».

Повторение имени — прямое нарушение запрета, хотя бот при этом отказался выдавать номер. Политика должна проверять не намерение ответа, а фактический финальный текст.

В текущем локальном коде осталась одна ошибка Премиума: специальное краткое ветвление срабатывает только при буквальном вхождении `«премиум»`, но не на словоформу `«премиального»`.

### 3.6. Задвоения и длина ответа

В этом прогоне точное повторение предложений в ответе не воспроизвелось: 0 из 160 и на dev, и локально. Оно также не появилось на пяти запросах с намеренно повторенным входным текстом. Это положительный результат, но он не отменяет задвоения со скриншотов: такой кейс нужно оставить обязательным регрессионным тестом по конкретной исходной формулировке.

Все ответы уложились в технический лимит 900 символов. Однако два ответа о подключении Премиума длиной около 720 символов формально краткие, но содержательно перегружены нерелевантным блоком о демо и договорных данных. Поэтому одной проверки длины недостаточно.

## 4. Оценка качества LLM

### Что можно утверждать

- `qwen-plus` использован в 40/160 запросов — 25%; 75% ответов нельзя оценивать как ответы LLM.
- На Qwen-подмножестве верный маршрут был у 20/40 — 50%.
- При верном маршруте обязательные смысловые маркеры сохранены в 20/20.
- Полностью прошли приемку 16/20 корректно маршрутизированных Qwen-ответов — 80%.
- Три из четырех отклонений при верном маршруте связаны с запрещенным содержанием: два лишних упоминания демо и одно повторение имени. Четвертое — ответ с полезным описанием тарифов технически имел `resolution=clarified`, хотя тест ожидал прямую реакцию.
- Точных повторов предложений Qwen не создал.

### Чего по этому прогону утверждать нельзя

Нельзя честно измерить «на сколько процентов Qwen лучше/хуже без LLM», потому что:

1. dev и локальная рабочая копия имеют разные версии маршрутов и контента;
2. LLM вызывается неслучайно, а только на части типов ответа;
3. нет доступа к снимку БЗ, который фактически находится внутри развернутого контейнера;
4. ответы `mock` и `qwen-plus` относятся к разным по сложности выборкам.

Для чистого вывода нужен один и тот же build, одна и та же БЗ и два режима на одном стенде: `LLM_ENABLED=false/true` с одинаковыми входами и фиксированными версиями модели и prompt.

### Практический вывод по LLM

LLM сейчас не является главным источником провала, но усиливает его внешнее впечатление: ошибочный сценарий превращается в связный, уверенный и иногда длинный неправильный ответ. До исправления route layer расширять долю LLM-вызовов нельзя.

## 5. Почему штатный production-gate не выявил проблему

Текущий gold-набор показывает:

- 312/312 верных сценариев;
- 100% покрытия обязательных фактов;
- production gate — passed.

Независимый набор показывает 43,75% верного маршрута на dev и 53,12% локально. Причина расхождения: старый набор слишком близок к известным формулировкам и проверяет в основном уже описанные `positive_examples`. Новый набор специально не копирует их; точное пересечение — **0 из 160**.

Таким образом, существующий gate полезен как регрессия известных фраз, но не является доказательством готовности к реальным пользователям.

## 6. Корневые причины

### P0. На dev развернут не текущий код

Фактически загруженный виджет использует ассеты `20260812-chat-home`; текущая рабочая копия — `20260813-answer-quality`. На dev кнопка «В начало» находится в HTML без стартового скрытия. Dev также не знает новый маршрут `transfer.seller_no_response`, что подтверждается результатом 0/20 против 11/20 локально.

Без явного build SHA и версии БЗ невозможно надежно понимать, что именно тестируется и что было доставлено.

### P0. Сценарный матчинг слишком зависит от точных слов

`_example_score` использует точное пересечение нормализованных токенов. Он не применяет лемматизацию, исправление опечаток и символьное сходство к каждому токену. При замене, перестановке букв или другой словоформе пример быстро теряет баллы. Сценарий принимается только при достаточно высоком абсолютном score и отрыве от второго кандидата.

Отдельный fuzzy-механизм есть, но он не образует единую нормализацию для всех ступеней маршрута. В результате intent, scenario engine и поздний knowledge search могут опираться на разные сигналы.

### P0. Неоднозначность и `out_of_scope` определяются хрупкими регулярными выражениями

Правила общего адреса и возврата рассчитаны на ограниченный порядок слов и правильное написание. Фразы `«ваш адрес»`, `«находитесь вы где»`, `«деньги обратно как»` или варианты с ошибками не получают ожидаемое уточнение.

### P0. LLM получает только один уже выбранный контекст

При неверном `scenario_id` Qwen не видит альтернатив и не может сказать маршрутизатору, что статья противоречит вопросу. Отсюда «Росгосстрах не отвечает» → адрес стоянки и «Совкомбанк Страхование потерялось» → правила ОСАГО.

### P1. Контент сценариев содержит смешанные ответы

Статья подключения тарифа объединяет подключение, демо, данные договора, безопасность документов и проверку статуса. Даже дисциплинированная LLM сохраняет лишний блок, потому что он присутствует в разрешенном контексте.

### P1. Финальный safety/content guard неполон

Проверка имен опирается на регулярные выражения и может извлечь слово рядом с глаголом вместо фактического имени. Нет финального универсального правила «не повторять PERSON из запроса» и нет запрета на demo-факты для intent подключения Премиума.

## 7. Что исправлять

### Этап 1 — релизная дисциплина, до любых новых промптов

1. Не продвигать текущий dev build в production.
2. Развернуть frontend и backend атомарно из одного commit SHA.
3. Возвращать в `/health` и диагностическом заголовке:
   - commit/build SHA;
   - версию `scenarios.json`;
   - хэш БЗ;
   - версию prompt;
   - активную модель и provider;
   - версию ассетов виджета.
4. В smoke-тесте после деплоя сравнивать эти значения с ожидаемыми.
5. Устранить кеширование старых widget assets или использовать content hash в имени файла.

### Этап 2 — единый устойчивый route layer

1. Перед любым сравнением применять одну цепочку:
   - Unicode/регистр/`ё`;
   - исправление распространенных опечаток;
   - лемматизация или стемминг;
   - нормализация доменных сущностей и страховых;
   - token-level fuzzy и char n-gram similarity.
2. Переделать `_example_score`, чтобы он сравнивал исправленные/лемматизированные токены, а не только точное множество слов.
3. Не требовать полного совпадения всех слов многословной фразы для fuzzy match.
4. Объединить сигналы intent, scenario engine и knowledge search в один ранжированный результат с диагностикой score/margin.
5. Если есть сильный доменный признак, не отдавать `out_of_scope`; при малом margin задавать предметное уточнение.

### Этап 3 — обязательные детерминированные маршруты

Сделать до semantic/LLM-слоя:

- `[страховая/название продавца] + [не отвечает/молчит/нет связи] + [лот/выигрыш/передача]` → `transfer.seller_no_response`;
- общий адрес/местонахождение организации → уточнение «офис / осмотр / получение лота»;
- общий возврат/вернуть деньги → уточнение вида возврата;
- явное подключение `преми* + подключ*/оформ*/активир*` → `tariff.connect`;
- `ставка + сделать/поставить/подать` → `bid.place`;
- `получить/забрать + выигранный/оплаченный лот` → `pickup.receive_lot`;
- `статус/закончились + торги/аукцион` → `auction.status`.

Реестр страховых должен включать проверенные формы из этого набора и поддерживать опечатки: Согласие, СберСтрахование, Совкомбанк Страхование, Зетта, Югория сейчас не покрыты полностью.

### Этап 4 — разделить контент и типы реакции

1. В `tariff.connect` оставить только 2–4 предложения о подключении и проверке активации.
2. Демо, договорные данные и тип пользователя вынести в отдельные сценарии и кнопки.
3. `refund.eligibility` сделать информационным ответом без автоматической эскалации; эскалировать только конкретную операционную проверку.
4. Общий возврат всегда сначала уточнять.
5. Для каждого сценария явно хранить `response_policy`: `answer`, `clarify`, `offer_ticket`, `status` — без повторного угадывания по общему intent.

### Этап 5 — LLM как контролируемый слой

1. Не использовать свободную генерацию для исправления неопределенного маршрута.
2. При низком score можно вызвать отдельный классификатор, который выбирает только из 3–5 `scenario_id` по JSON-схеме или возвращает `clarify`.
3. Генератору передавать только минимальный approved answer выбранного сценария, а не смешанную статью.
4. После генерации проверять:
   - имя сотрудника из запроса не появилось в ответе;
   - нет фактов из запрещенных секций;
   - присутствуют обязательные факты;
   - нет новых чисел, адресов, email и обещаний, которых нет в approved context;
   - ответ не длиннее заданного сценарного лимита.
5. При нарушении возвращать детерминированный approved answer, а не текст модели.

## 8. Новый обязательный release-gate

Предлагаемые минимальные пороги:

| Метрика | Порог выпуска |
|---|---:|
| Полный `answer_hit` на независимом наборе | ≥ 80% |
| Верный сценарий + intent | ≥ 85% |
| Опечатки | ≥ 80% |
| Перестановленные буквы | ≥ 75% |
| Разные словоформы | ≥ 85% |
| Названия страховых и отсутствие ответа | ≥ 90% |
| Правильное уточнение неоднозначных запросов | ≥ 90% |
| Полностью пройденные диалоги | ≥ 80% |
| Повторение имен сотрудников | 0 случаев |
| Лишняя информация о демо при подключении Премиума | 0 случаев |
| Точный повтор предложений | 0 случаев |
| Уверенно неверный сценарий | ≤ 2% |
| HTTP-успешность | 100% |
| Qwen p95 | ≤ 5 секунд |

Gold-набор 312 кейсов нужно сохранить как базовую регрессию, но production-gate должен проходить **оба** набора. Новые запросы из обращений поддержки следует еженедельно добавлять в отдельный blind/holdout-набор, не копируя их сразу в `positive_examples` до измерения.

## 11. Ограничения аудита

- Dev — black-box проверка. Внутренний commit SHA и снимок БЗ API не публикует.

- Тикеты и внешние письма намеренно не создавались.
